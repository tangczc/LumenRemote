# Lumen Remote

低延迟远程桌面 / 游戏串流。Windows 桌面客户端 + 自研传输引擎，4K60 硬件编码，
跨公网点对点直连，端到端加密。

- **P2P 优先**：IPv6 直连 + NAT-PMP/UPnP 端口映射 + 并行打洞 + 落中继后自动升级回 P2P
- **自研 UDP 协议**：20 字节定长头、多通道复用、XOR 前向纠错、分片级重传
- **端到端加密**：X25519 + HKDF + AES-256-GCM，中继无法解密
- **双信号拥塞控制**：时延梯度提前感知排队，丢包信号兜底
- **4K60 能力**：ddagrab GPU 采集 + NVENC 硬件编码，实测 3840×2160@60 稳定出流
- **分辨率跟随控制端**：被控端直接把本机显示器切到控制端的分辨率，编码 1:1 不缩放
  （控制端 2560×1440 → 本机切 2560×1440，连 DPI 缩放一起重算）；会话结束自动恢复原分辨率
- **单窗口应用**：左侧导航 + 远程协助面板，同时具备被控与主控能力
- **持久设备 ID**：重启后仍是同一个 9 位 ID，可长期寻址

## 这个项目是什么

**Lumen Remote** 是一个从零自研的远程桌面 / 游戏串流产品，对标 UU 远程、向日葵这类工具：

- **被控端和主控端都是同一个 Windows 桌面应用**（Electron 壳 + Node 引擎）：一个窗口里既能被人远程协助，
  也能主动去连别人；
- **传输层完全自研**：UDP 协议、XOR 前向纠错、分片级重传、双信号拥塞控制、pacer，
  X25519 + HKDF + AES-256-GCM 端到端加密，中继只看得到密文；
- **连接优先 P2P**（IPv6 / NAT-PMP-UPnP 端口映射 / 并行打洞），打不通才落到自建服务器的 UDP 中继，
  落到中继后还会在后台继续尝试打洞并自动升级回直连；
- **安卓控制端**用 Kotlin + MediaCodec 硬解，手机 / 平板都能用，支持外接键鼠和中文输入法；
- **不依赖任何第三方远控内核**（没有 VNC / RDP / WebRTC 依赖）；信令 + 中继也是本仓库里的一套 Node 程序，
  一条脚本就能部署到 Ubuntu 24.04。

画面按控制端的视口编码：被控机会临时把显示器切到控制端的分辨率（连 DPI 一起重算），
会话结束原样恢复，包括多显示器的相对位置。

## 还没完成 / 已知限制

**产品面**

- 没有账号体系和设备列表：设备 ID 已持久化，但仍靠手工抄写 9 位码；
- iOS / macOS / Linux 客户端未开始（协议层已与平台解耦，安卓那套 Kotlin 实现可作参考）；
- 安卓端只能**控制**电脑，不能作为被控端（需要 MediaProjection + 无障碍服务）；
- 剪贴板同步、文件传输、音频转发都还没做（协议里留了通道）；
- 多屏切换未做：目前编码主显示器，控制端看不到副屏；
- 中继是单台单地域服务器，没有 PoP 和带宽调度；信令链路仍是明文 TCP。

**技术面**

- 输入注入走 `SendInput`：只认原始输入的全屏游戏（反作弊）收不到，需要驱动级方案；
- 显示器接管靠 `ChangeDisplaySettingsEx` + DDC，不带虚拟显示器驱动（IddCx 需要 EV 签名）；
- 候选地址只有 IPv4，`UdpLink` 的 `udp6` 双栈尚未接通；
- GCM nonce 的 32 位序号在 4K60 满载约 3 小时后回绕，需要中途重协商；
- 弱网只做分片级重传，整帧丢失时会花屏到下一个 IDR。

**关于仓库**：`docs/`（设计文档、路线图、部署细节）和 `build/`（引擎打包产物）不随仓库提交；
打安装包前需要自备 `ffmpeg.exe` 放到 `vendor/ffmpeg/`（见「打包安装程序」）。

## 运行桌面客户端

```bash
npm install
npm run desktop        # 打包引擎 + 启动 Electron 客户端
```

首次运行会自动在本机启动信令服务（TCP 7801 / UDP 7802）。

### 打包安装程序

```bash
npm i -D electron-builder
npm run dist           # 产出 release/LumenRemote-0.1.0-setup.exe
```

在国内网络下需要镜像环境变量，否则 electron 与 nsis 二进制会卡在下载：

```powershell
$env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
$env:ELECTRON_BUILDER_BINARIES_MIRROR="https://npmmirror.com/mirrors/electron-builder-binaries/"
npm run dist
```

不想联网、或 `npm run dist` 一直卡在下载 electron 时，用仓库里的脚本（改用本机
`%LOCALAPPDATA%\electron\Cache` 里已经下过的运行时，全程离线）：

```powershell
.\scripts\build-win.ps1                            # 环境检查 + typecheck + 单测 + build:engine + 出包
.\scripts\build-win.ps1 -SkipChecks                # 跳过检查，只出包
.\scripts\build-win.ps1 -Output out-build -Clean   # 换输出目录（release 被占用时），并清理解压出的运行时
```

脚本会顺手校验「包内引擎 == 本次 build」和「包内带 ffmpeg」，最后打印安装包大小与路径。
超过一次 `EBUSY` 时会自动等 10 秒重试一轮。

**ffmpeg 随包发布**：把 `ffmpeg.exe` 放到 `vendor/ffmpeg/`（该目录不进仓库，需自备；`npm run build:engine`
会拷进 `build/ffmpeg/`，`extraResources` 再带进安装包的 `resources/engine/ffmpeg/`）。
不打包的话，一台没装过 ffmpeg 的电脑被控时会直接 `spawn ffmpeg ENOENT`：没有画面，
控制端等 8 秒判定「对方已离线」。装上以后安装包大约 179 MB（其中 ffmpeg 220 MB 未压缩）。

查找顺序：`vendor/ffmpeg`/随包的 `ffmpeg/` → `RD_FFMPEG` 环境变量 → PATH → winget / chocolatey /
`C:\Program Files\ffmpeg\bin`；都没找到时启动日志会直接报「未找到可用的 ffmpeg」。

## 开发模式

```bash
npm install
npm run app            # 统一客户端（自带信令），打开 http://127.0.0.1:7800
```

单独起信令服务（跨机部署时用）：

```bash
npm run signal -- --port 7801 --udp 7802 --bind 0.0.0.0
```

### 常用参数

```bash
# 合成画面代替真实屏幕，便于无 GUI 环境验证
npm run app -- --source test

# 跳过确认弹窗（仅调试）
npm run app -- --auto-accept

# 使用固定验证码代替每次启动随机生成的验证码
npm run app -- --password 123456

# 连接公网信令，不启动本机信令
npm run app -- --signal 203.0.113.10 --port 7801 --no-signal-host

# 启动后直接连接某个设备（必须同时给出对方的验证码）
npm run app -- --code 123456789 --password 987654
```

| 参数 | 说明 |
|---|---|
| `--signal <host>` | 信令服务器地址（默认 `124.221.215.145`，公网服务器） |
| `--port <port>` | 信令 TCP 端口（默认 `7801`） |
| `--ui <port>` | 本地面板端口（默认 `7800`） |
| `--no-open` | 不自动打开浏览器 |
| `--no-signal-host` | 不启动本机信令服务 |
| `--quality office\|balanced\|game\|uhd` | 画质档（4K60 = 45 Mbps） |
| `--source screen\|test` | 采集源 |
| `--encoder auto\|libx264\|h264_nvenc\|h264_qsv\|h264_amf` | 编码器 |
| `--password <pwd>` | 使用固定验证码，代替每次启动随机生成的验证码 |
| `--inject true\|false` | 是否允许注入远端键鼠 |

### 验证码

没有「免验证码」这个状态。首页「本设备」卡片右侧是验证方式，三种都会生成真实验证码，区别只在有效期：

| 验证方式 | 有效期 | 适用 |
|---|---|---|
| **单次验证码**（默认） | 本次启动；一个会话结束立即更换 | 临时求助，最安全 |
| **今日验证码** | 当天不变，跨零点自动更换 | 一天内多次连同一台机器 |
| **长期验证码** | 长期不变，由用户自设（4–16 位数字或字母） | 固定几台机器互连 |

验证码是 **6 位随机大小写字母 + 数字**（如 `rT8pQ3`），字符集刻意去掉了
`0/O/o`、`1/l/I` 这些容易看错的字形，剩下 56 个字符，6 位约 3.1×10¹⁰ 种组合。
**区分大小写**：手机端输入框关闭了自动大写与自动纠错，照着屏幕上抄即可。

验证码默认打码显示，点右侧眼睛查看；复制图标一次复制「识别码 + 验证码」。
设置里的「长期验证码」同样默认打码，核对时点眼睛展开。
单次与今日验证码都由本机生成，今日验证码由本机密钥与日期派生，均不写进日志。
比对分两处，缺一不可：

1. 信令服务在 `accept` 阶段比对发起方提交的验证码；
2. **被控端拿到 `ready` 后再用本机验证码比对一次**——信令服务被改过、或前端替用户
   点了「接受」，都开不了会话，因为验证码只存在被控端。被控端回给服务的永远是
   自己的验证码，前端没有接口能指定它。

两处都是「忽略首尾空格、字符逐位精确比较」，任何一侧缺失或大小写不一致都会直接拒绝。

## 端角色

| 平台 | 主控（发起连接） | 被控（接受连接） |
|---|---|---|
| Windows | ✅ | ✅ 双向互控 |
| Android | ✅ | ❌ 控制端专用（会话自动横屏） |
| iOS / iPad | ⬜ 未实现 | ❌ 只做控制端 |

角色由客户端在信令 `hello` 里声明（`hostable`），信令服务据此拒绝任何指向控制端的
连接请求（返回「XXX 是控制端，不支持被控」），而不是让请求在手机上悬空。

### 被控时的迷你面板

本机被控时窗口不会占满屏幕，而会缩成右下角一个置顶小卡片，显示对端名称、FPS、延迟、
码率、数据通道（P2P / 中继）和 SAS 校验码，右下角是「断开」。点「收起」变成一条只显示
「正在被控」的窄条，点「展开」恢复；会话结束后窗口自动回到原来的位置和大小。

对端如果直接消失（手机关机、断 Wi-Fi）来不及发 `bye`，本机会在 8 秒无心跳后自动结束会话
并退出迷你面板，不会卡在小窗里。

### 让出显示器（分辨率跟随控制端）

UU / 向日葵被控时本机屏幕会黑掉，看起来像显示器被接到了控制端。**真正的做法是装一个签名过的
虚拟显示器驱动（IddCx）**，会话开始时凭空多出一块「控制端尺寸」的显示器，桌面画到那块屏上，
采集也从那里取。本项目没带驱动，走的是等价路线——**把本机真实显示器切到控制端的分辨率**：

1. **切换分辨率**：控制端 `2560×1440` → 本机真的切成 `2560×1440`，编码器 1:1 采集，
   不付缩放代价。Windows 连 DPI 缩放都会跟着重算（实测 4K 175% → 1440p 125% → 恢复 4K 又回到
   175%），效果和「把一块 1440p 显示器插到这台机器上」一致。
2. **面板没有该分辨率时**：优先选同宽高比且刚好覆盖的档位，其次选最大的同比例档位；
   都没有（例如 20:9 的手机）就保持本机分辨率、按原逻辑缩放输出。

会话结束（对方断开、超时、本机主动断开）会把**分辨率、刷新率、以及每台显示器的位置**一起恢复原样；
进程被杀的话下次启动会读到 `app-state.json` 里的恢复标记并自动还原。

> 多显示器注意：主屏缩小分辨率时，Windows 会把相邻的副屏**夹到主屏旁边**（不允许留空隙），
> 所以会话期间副屏在系统里看起来会挪一下——但会话结束会按记录的位置精确放回去（实测
> `DISPLAY1 3840x2160@121 @0,0 + DISPLAY2 2160x3840@60 @3840,0` 进出完全一致）。
> 若想连这一步都不发生，只能上虚拟显示器驱动。

首页「本设备」卡片上有两个独立开关：

| 开关 | 默认 | 作用 |
|---|---|---|
| **让出显示器** | 开 | 会话期间切到控制端分辨率，编码 1:1 |
| **会话时黑屏** | 关 | 通过 DDC/CI 把本机亮度调到 0；需要显示器支持 DDC/CI（多数笔记本内屏不支持） |

黑屏为什么不用 DPMS 关显示器：实测关掉输出后 ddagrab 直接 0 帧（控制端会定格在最后一帧），
而 DDC/CI 亮度归零时系统认为显示器正常，仍能跑满 60fps。黑屏默认关闭，是因为万一恢复失败，
用户会面对一块黑屏又没法点界面上的按钮。

> 想让手机 / iPad 的非标准分辨率也「原样出现」（`2400×1080`、`2732×2048`），就必须带
> 一个 IddCx 虚拟显示器驱动。IddCx 框架本身免费（Windows 驱动工具包自带），花钱的是驱动签名。

## 安卓控制端

`release/LumenRemote-android-0.1.0.apk`（0.69 MB，minSdk 26 / targetSdk 36）。

```bash
cd android
./gradlew :app:assembleRelease      # 或直接用 Android Studio 打开 android/
adb install -r app/build/outputs/apk/release/app-release.apk
```

用法：信令服务器默认就是公网地址 `124.221.215.145`（开箱即用），只需填桌面端的 9 位识别码和验证码，
点「连接」。想直连局域网（更快、不依赖公网服务器）就把信令服务器改成电脑的局域网 IP，或点「自动发现」。
点下「连接」后立刻弹出等待卡片（转圈 + 「等待 XXX 的电脑同意…」+ 取消）；对方点「允许协助」
后自动进入会话，点「拒绝」则卡片变红显示「对方拒绝了连接」，需要点「知道了」才关闭。
连上后自动**横屏**全屏显示桌面，单指移动=鼠标、点按=左键、双指上下滑=滚轮、底部「右键」切换为右键单击。
退出会话自动恢复竖屏。

### 平板（7" / 11" / 13" / 14.6" 实测）

首页按**窗口宽度**（不是最小宽度）决定单列还是双栏：两栏各自至少要有 320dp（最窄的常见手机宽度），
内容占窗口 94% 并留 10dp 栏间距，于是分栏临界点落在 **≈692dp**。这样 600dp 的 7-8" 平板竖着是单列
（两栏各 280dp 会挤成一团），而所有 11" 以上平板和书本式折叠屏展开后都是双栏。

窗口尺寸一变就重排，不用重启 App：折叠屏展开/合上、分屏、Samsung DeX、小米桌面模式、
iPad Stage Manager 这类自由窗口都能正确切换（实测同一进程在 1280dp↔600dp 之间来回切，双栏↔单列即时生效）。

按各机型**固件 densityDpi** 复现的窗口尺寸（AVD 上用 `wm size` + `wm density` 逐一验证）：

| 设备 | 屏（寸） | 分辨率 | density | 竖屏窗口 | 首页布局 |
|---|---:|---|---:|---|---|
| Nexus 7 (2013) | 7.0 | 1200×1920 | 320 | 600×960 dp | 单列 |
| Fire HD 8 (2020) | 8.0 | 800×1280 | 213 | 601×962 dp | 单列 |
| OnePlus Open（内屏） | 7.8 | 2268×2440 | 520 | 698×751 dp | 双栏（各 326dp） |

口径说明：Android 的 dp 用**固件逻辑密度**（`ro.sf.lcd_density` / MIUI `persist.miui.density_v2`）算，
不是屏幕 ppi——所以 14" 的小米平板和 11" 的小米平板同为 720dp，而 13" iPad 是 1032pt。
density 数据来自各家固件 `build.prop`，机型分辨率取自厂商/GSMArena 规格页；iPad 为 2× Retina 逻辑点。
分辨率本身不影响布局（视频永远按比例居中、四周留黑边），只有 dp 宽度影响。

其他边界也测过：分屏到 320×480dp 时仍是单列并可滚动；系统字体放大到 1.3× 时不截断、不重叠；
13"/14.6" 这类超宽窗口内容按 1080dp（≥1600dp 窗口时 1320dp）封顶居中，不会被拉散。

会话里平板同样是整屏视频 + 更大的底部工具栏，触摸坐标按视频矩形换算：真机 3200×1440 横屏、
被控端 3840×2160，三组落点实测误差 ≤ 1px。

识别码输入框**只能填数字**，并且按 3 个一组分隔（`415 563 885`）。这件事在国产输入法上比看起来难，
踩了三轮才稳：

- 直接在文本变更回调里改写缓冲区 → 抛 `setSpan ends beyond length` 闪退；
- 用定时器整体 `setText` → 输入法组词区还没结束，它会把不带空格的原文再提交一遍，空格"消失"；
- 只在缓冲区里原地插空格 → 同样被组词区覆盖（实测格子里的空格留不住）。

最终做法：打字停顿 320ms 后，先 `removeComposingSpans` 结束组词区，再整体重排、按"第几个数字"还原光标。
实测输入法批量注入、逐键快打、每 700ms 慢打三种节奏都得到 `123 456 789`，字母打不进去，退格一次删一位。

### 软键盘与中文输入

会话里点底部「键盘」会拉起手机输入法，输入的内容按"提交"转发到电脑。中文/日文这类需要**组词**的语言，
拼音只会留在手机本地的组词区：只有选中候选词、输入法真正提交那一下，字符才发给电脑，所以电脑上不会
冒出一串拼音字母。

- 组词区判断用 `BaseInputConnection.getComposingSpanStart()`，组词期间一律不转发、也不清空缓冲区
  （以前直接清空会打断输入法，候选词根本出不来）；
- 提交的中文/emoji/非美式键盘字符按 Unicode 文本注入（`KEYEVENTF_UNICODE`），走的是 `kr` 消息；
- 退格走 `deleteSurroundingText`（捕获缓冲区是空的，所以由我们自己转成 Windows 退格键），
  回车走键盘映射表（扫描码 `0x1c`），手机输入法的回车键同样生效；
- 电脑端注入器的 stdin **显式按 UTF-8 解码**：原先用 `[Console]::In` 会按系统 OEM 代码页（GBK）解，
  中文在到达 `SendInput` 之前就已经变成乱码了 —— 这是"安卓输入不了中文"的真正原因之一；
- 会话里底部工具栏按钮都设成不可获取焦点，否则按回车会被那个按钮当成"点击"，历史上曾因此误触「挂断」。

实测（真机 + Windows 记事本）：拼音 `nihao` 选词后电脑上落下「怒海」；手机退格能删掉电脑上的字符；
字母 `ab` 与回车都能正常落字（回车在记事本里换行）。


> 默认已经走公网服务器（`124.221.215.145`），手机和电脑各自联网就能直接连。
> 下面这套局域网方式只是**更快、且不依赖公网服务器**的可选做法。

1. 在 Windows 上启动客户端，界面「本设备」卡片底部会直接显示要填的地址：
   ```
   手机端「信令服务器」填  192.168.8.242
   ```
   只有一块网卡能出去时，直接点旁边按钮复制即可。虚拟网卡（VMware `VMnet*`、
   Hyper-V、WSL、Docker）和 `169.254.x.x`（DHCP 失败）已经自动过滤，不会显示出来。
2. 手机连同一个 Wi-Fi，点「信令服务器」右边的**自动发现**：App 向 UDP 7802 广播
   一个 `0x01` 探测包，桌面端按来源地址单播回复自己的 IP 和 TCP 端口，App 自动填好
   并建立信令连接。找不到时再手填上面的地址。
3. 填 PC 的识别码与验证码，点「连接」。首次监听时 Windows 会弹防火墙提示，选
   「允许访问」；安装版已自带放行规则（`Lumen Remote` 入站 TCP/UDP，覆盖 Public 配置文件）。

地址填错（例如把 `192.168` 写成 `192.198`）会以 `ECONNREFUSED` 结束，App 日志会打印
本机地址并提示「不在同一网段，地址可能填错了」，随后自动退回一次广播发现。

如果卡在「正在连接信令服务器」，在 PC 上以管理员身份补一条放行规则：

```powershell
New-NetFirewallRule -DisplayName "Lumen Remote LAN" -Direction Inbound -Action Allow `
  -Protocol TCP -LocalPort 7801 -Profile Any
New-NetFirewallRule -DisplayName "Lumen Remote LAN UDP" -Direction Inbound -Action Allow `
  -Protocol UDP -LocalPort 7802 -Profile Any
```

实现要点：

- **协议层完全重写为 Kotlin**，与桌面端共用同一套 20 字节报文头、分片格式、XOR FEC、
  AES-256-GCM 记录层和信令 JSON，因此两端可以直接互通，不需要网关
- **X25519 用 BigInteger 实现**（Android 的 XDH KeyAgreement 要 API 33），启动时用 RFC 7748
  向量自检，失败会直接显示在首页日志里
- **MediaCodec 异步解码到 SurfaceView**，从 SPS 解析分辨率并在变化时重建解码器；
  SurfaceView 按视频宽高比布局，避免拉伸
- **所有 UDP 收发都在独立线程**（Android 主线程禁止 socket I/O），输入事件经发送队列出队
- 网络路径与桌面端一致：并行打洞 → P2P，失败回落到中继

> 安卓端是**控制端专用**：它注册到信令时声明 `hostable: false`，因此不会被 Windows 拨打，
> 首页也不再显示本机识别码。让安卓被控需要 MediaProjection 采屏 + 无障碍服务注入，不在本产品范围内。

## 键鼠控制

**结论：不自建虚拟键鼠，直接复用被控端自己的键鼠栈**（`SendInput`）。远程注入的按键对系统来说
和本机键盘没有区别，输入法、快捷键、系统级热键、每个应用的键盘处理全部原生可用；自建一套虚拟
HID 需要签名驱动，收益只在「只认原始输入的游戏」，这一项留作后续可选项。

### 鼠标

| 模式 | 触发 | 做法 | 精度 |
|---|---|---|---|
| 绝对定位 | 默认（桌面操作） | 画布坐标 → 0..65535 → `MOUSEEVENTF_ABSOLUTE` | **1:1 像素精确**（实测 25%/25% → 960,538） |
| 相对移动 | 点画面捕获鼠标后 | `movementX/Y` → 逐像素 `MOUSEEVENTF_MOVE` 批量注入 | **1:1**（200,120 → +199,+120） |

两个坑都踩过并修好了：

- **注入进程必须声明 DPI 感知**。否则在 175% 缩放下「点击画面中心」会落到 `1097,616` 而不是
  `1920,1080`——坐标被系统按缩放虚拟化了一遍。现在注入器启动时先 `SetProcessDpiAwarenessContext`。
- **相对移动会被本机的「提高指针精确度」放大**。实测 10px 注入变成 22px、200px 变成 911px。
  现在把一次移动拆成逐像素的批量 `SendInput`，每个子步都低于加速阈值，从而得到真正的 1:1，
  同时保留用户自己的指针速度设置。

### 键盘

`keydown`/`keyup` 走 **扫描码**（PC set-1）+ 虚拟键码，扩展键用 `0x1xx` 标记，因此
`Ctrl/Alt/Shift/Win`、方向键、功能键、数字键盘、`PrintScreen/ScrollLock/NumLock`、菜单键
在宿主上都是真实的按键事件；长按交给宿主的自动重复处理，不重复发包。没有固定扫描码的字符
（非美式布局、输入法产出的文字）走 Unicode 文本通道 `kr`。

### 安卓 / iPad

| 场景 | 行为 |
|---|---|
| 纯触屏 | 单指点击=左键、拖动=移动、双指上下滑=滚轮，底部「右键」按钮切换下一次点击为右键 |
| 外接鼠标 | 悬停即移动光标（绝对模式）；左中右键、侧键都按真实按键注入；滚轮走 `AXIS_VSCROLL` |
| 外接鼠标 + 「鼠标锁定」 | `requestPointerCapture()` 后改用 `AXIS_RELATIVE_X/Y`，和 PC 的捕获模式一致 |
| 外接键盘 | `onKeyDown/KeyUp` 映射成扫描码注入，长按不重复发包；没有扫描码的字符走文本通道 |
| 软键盘 | 底部「键盘」按钮拉起输入法，输入法提交的字符（中文、emoji 都行）走文本通道；退格会转成 Backspace |

> `iOS/iPad` 客户端尚未实现；协议层已经支持上面全部输入形态（绝对/相对/按键/文本），
> 移植时按同样映射即可。

## 跨公网部署

默认只在本机跑信令，用于局域网或本机自测。要让两台不同网络的机器互连：

### 一键部署（Ubuntu 24.04，全新机器）

[scripts/deploy-ubuntu.sh](scripts/deploy-ubuntu.sh) 把「装 Node → 建系统用户 → 装成
systemd 服务 → 放开防火墙端口 → 打印客户端该填什么」全做完：

```bash
# 1) 本机（Windows）上先产出信令单文件
npm run build:engine          # 产物：build/signaling-main.mjs（约 18 KB，自包含）

# 2) 把两个文件传到服务器
scp build/signaling-main.mjs scripts/deploy-ubuntu.sh root@<你的服务器>:/root/

# 3) 服务器上一条命令
ssh root@<你的服务器> 'bash /root/deploy-ubuntu.sh'
```

脚本做的事：装 Node.js 24 LTS（npmmirror 优先、官方源兜底，**下载完比对官方 SHA-256，
不匹配立即中止**）→ 建无登录系统用户 `lumen`
→ 装到 `/opt/lumen-signal` → 写 `/etc/systemd/system/lumen-signal.service`（开机自启、
崩溃 2 秒后自拉、`LimitNOFILE=65535`、`ProtectSystem=strict` 等沙箱项）→ 调 UDP 缓冲上限
→ 启动并验证端口在监听 → 放行 ufw → 打印公网 IP 和客户端填法。

```bash
bash deploy-ubuntu.sh --port 9001      # 换端口，UDP 自动用 9002
bash deploy-ubuntu.sh --public 1.2.3.4  # 手动指定中继地址（默认自动探测公网 IP）
bash deploy-ubuntu.sh --uninstall      # 卸载（Node 保留）
```

脚本会自动探测公网 IP 并作为 `--public` 传给信令服务（中继地址）。这一项必须对，
否则**打洞失败的连接会一直超时**：中继地址错了，两端把媒体发到一台没有中继的主机上，
双方都收不到心跳，8 秒后互相判定「对方已离线」。

重复执行是安全的：会替换程序并重启，不会重复建用户或改端口。脚本用 shellcheck
（`-S style`）检查通过，但**没有在真机上跑过**——第一次部署如果报错，把输出贴出来即可。

> 唯一脚本改不了的一步：云厂商**安全组**里要放行 `TCP 7801` 与 `UDP 7802` 入站。
> 只开 TCP 的典型症状是「信令连上了、设备显示在线，但永远连不出画面」。

### 手动部署

1. 在一台有公网 IP 的服务器上运行信令：
   ```bash
   node signaling-main.mjs --bind 0.0.0.0 --port 7801 --udp 7802 --public <服务器公网IP>
   ```
   `--public` 是给**中继**用的地址：打洞失败时两端把媒体发到「这个地址 + UDP 端口」，
   服务器负责转发。云主机的网卡上通常只有内网地址（公网 IP 是 1:1 NAT），不写 `--public`
   就会把中继指到一台不可达的主机上，对端等到超时。本机直连公网、能直接看到公网 IP 时可以省略。
2. 放通 TCP 7801 与 **UDP 7802**（UDP 用于地址发现与打洞失败时的中继）。
3. 两台客户端在「设置 → 连接」中填写该公网地址并保存。

连接顺序：全部候选**同时**打洞（含服务端观测到的公网反射地址与服务端观测的 IPv6），
任一方向成功即锁定 P2P；全部失败自动回落到中继，业务不中断。

P2P 一共有四条路径，任何一条打通就不用中继：

| 路径 | 优先级 | 适用场景 |
|---|---|---|
| **IPv4 打洞**（主力） | 100 / 200 | 双方家用路由器的锥形 NAT，覆盖绝大多数家庭网络 |
| 路由器端口映射 | 400 | 路由器支持 NAT-PMP/UPnP 时，直接开公网端口给对端 |
| IPv6 直连 | 300 | 双方都有公网 IPv6，完全不需要穿透 NAT |
| 局域网直连 | 100 | 同一 LAN |

| 手段 | 说明 |
|---|---|
| **IPv4 打洞** | 服务端把观测到的公网映射作为 srflx 候选下发，双端同时向全部候选发包，任一方向通即成功 |
| **路由器端口映射** | 启动时尝试 NAT-PMP，失败回退 UPnP-IGD `AddPortMapping` |
| **IPv6 直连** | 双栈 socket，公网 IPv6 地址直接互通 |
| **优先级择优** | 多个候选同时应答时按优先级取最优，而不是「谁先回包用谁」——避免 hairpin NAT 绕路 |
| **中继→P2P 升级** | 已落中继的会话仍在后台按 1.5/3/5/8/12 秒递增重试打洞，成功即切回直连并提示用户 |

虚拟网卡（VMware/Hyper-V/WSL）候选被降到优先级 20，避免占用打洞窗口。
IPv4 打洞在**双端都是对称 NAT**（如运营商 CGNAT、部分企业网/移动网络）时会失败，
此时依次尝试端口映射、IPv6，都没有才落中继。
日志会打印当前能力：`UDP 双栈=true · 检测到公网 IPv6 地址` / `路由器端口映射成功 (natpmp) 外部 …`。

云端容量规划（带宽、包速率、成本、最小配置）见本地 `docs/deployment.md`。
一句话结论：纯信令几乎不耗带宽，4K60 的成本全在中继——
单会话往返 112 Mbps / 11.7k pps / 每小时 50 GB，且瓶颈是包速率而非带宽。
